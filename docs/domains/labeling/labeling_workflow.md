# 人工标注工作流

> 版本：v0.3
> 日期：2026-06-13
> 状态：第一阶段离线工作流。Mimics 是首个待验证工具，不是平台成立的前提。

## 1. 这套工作流要保证什么

第一阶段先保证五件事：

1. 每位标注者知道自己要处理哪些病例、图像序列和器官。
2. 保存中间进度不会被误认为最终标签。
3. 只有明确提交并通过自动检查，平台才创建人工确认标签。
4. 已提交标签仍可继续修订，但新结果不会覆盖旧版本。
5. 图像、标签、标注者、工具和空间关系都能追溯。

第一阶段不要求：

- 建设完整网站。
- 建设账号和复杂权限系统。
- 实现在线抢任务、超时回收和多人仲裁。
- 强制一组序列中必须有“主图像”和“参考图像”。
- 预先确定 Mimics 必须使用双 Python 运行环境。

## 2. 平台和标注者分别负责什么

### 2.1 平台负责

- 按患者、检查和序列整理数据。
- 检查去标识状态。
- 记录图像文件、空间信息和文件校验值。
- 创建标注任务和病例包。
- 准备可选的模型候选标签。
- 检查提交结果。
- 创建新的标签版本。
- 更新任务进度和问题报告。

第一阶段可以由平台操作者运行准备和收尾脚本。这个人也可以同时是标注者。

### 2.2 标注者负责

- 打开分配给自己的任务。
- 在指定图像序列上检查和修正指定器官。
- 随时保存中间进度。
- 结束工作时选择“提交完成”“提交复查”或“报告阻塞”。
- 对医学上无法确认的内容给出简短说明。

### 2.3 标注者不负责

- 手工填写标签生命周期。
- 计算文件校验值。
- 修改图像空间矩阵。
- 决定 nnUNet 标签编号。
- 决定标签能否进入所有训练任务。
- 手工整理平台要求的输出目录。

## 3. 一个病例可以包含多个序列

平台按下面层级理解数据：

```text
患者
-> 一次检查
-> 一个或多个图像序列
-> 一个病例工作单元
-> 一个或多个标注目标组
```

同一检查可以有平扫、动脉期和门静脉期。平台不默认哪一套是“主图像”。

标注任务直接说明每个序列需要处理哪些器官：

```yaml
image_sets:
  - image_id: img_noncontrast
  - image_id: img_arterial
  - image_id: img_venous

review:
  targets:
    - target_id: target_noncontrast_abdomen
      image_id: img_noncontrast
      organs: [liver, kidney_left, kidney_right]
    - target_id: target_arterial_vessels
      image_id: img_arterial
      organs: [liver, hepatic_artery]
    - target_id: target_venous_vessels
      image_id: img_venous
      organs: [liver, portal_vein]
```

如果只需要标一个序列，任务只列这个序列。其他序列可以留作查看上下文。

每份输出标签必须绑定自己的 `image_id` 和空间信息。没有明确配准关系时，不能把一个序列上的 mask 直接复制到另一个序列。

Mimics 中的“当前活动图像”只是软件运行时状态。工具适配器在处理某个目标组时负责切换到正确序列，不能根据用户最后点击了哪个序列来判断标签归属。

## 4. 保存、提交和标签状态

### 4.1 保存进度

标注者可以反复保存 `.mcs` 或其他工作文件并关闭软件。

保存进度只说明“工作可以继续”，不会：

- 创建新的正式标签版本。
- 把草稿升级为人工确认标签。
- 触发训练数据更新。

### 4.2 提交完成

标注者选择一个或多个完整目标组提交。平台导出这些目标组并运行检查。

检查通过后：

- 为每个通过的目标组创建新的人工确认标签版本。
- 记录标注任务、标注者、基础标签版本和工具信息。
- 将相应目标组标为完成。

检查失败后：

- 不覆盖旧标签。
- 目标组回到进行中。
- 生成标注者能看懂的问题报告。

### 4.3 提交复查

当标注者已经查看，但无法对某个目标组作出可靠医学判断时，选择“提交复查”。

平台保存：

- 当前草稿。
- 不确定的器官。
- 简短原因。
- 需要复查的目标组。

不确定性属于标注任务，不增加新的标签生命周期状态。底层标签仍是草稿。

### 4.4 报告阻塞

如果问题来自数据或工具，而不是医学判断，选择“报告阻塞”。例如：

- DICOM 缺片。
- 图像序列无法打开。
- Mask 绑定到了错误图像。
- 脚本失败。
- 图像与标签空间关系无法解释。

平台保存错误代码、病例和任务标识、预期结果、实际结果和建议动作。

## 5. 任务状态

第一阶段只保留五种任务状态：

| 状态 | 含义 |
| --- | --- |
| `ready` | 数据准备完成，尚未开始 |
| `in_progress` | 正在工作，或者提交检查失败后等待修正 |
| `needs_review` | 标注者明确提交了不确定结果，需要复查 |
| `completed` | 所有目标组都已通过提交检查 |
| `blocked` | 数据或工具问题使任务无法继续 |

“提交中”和“退回”不作为长期状态。第一阶段提交后立即检查：

```text
提交完成
-> 检查通过：目标组完成
-> 检查失败：目标组回到进行中，并生成问题报告
```

后续引入异步队列和多人审批时，再增加中间状态。

## 6. 为什么要有目标组

目标组是最小提交单位，通常表示“某个图像序列上的一组相关器官”。

例如：

```text
平扫：肝 + 胆囊
动脉期：肝动脉
门静脉期：门静脉
```

同一目标组中的器官一起提交完成或一起进入复查。不同目标组可以独立完成。

这样设计解决两个实际问题：

- 一个无法确认的血管不会阻塞同一病例中已经完成的腹部实质器官。
- 多位标注者可以处理同一病例的不同目标组，而不覆盖彼此结果。

## 7. 完整操作流程

### 7.1 进入标注工具前

平台操作者执行：

1. 从受控原始区读取数据。
2. 检查去标识状态；未通过时停止。
3. 按患者、检查和序列分组。
4. 为每个序列创建图像记录。
5. 保存文件校验值、图像空间信息和当前任务关心的器官覆盖情况。
6. 创建带 `target_id` 的标注任务。
7. 可选地运行候选标签生成脚本。
8. 检查基础图像和草稿标签是否可读、是否对齐。
9. 生成病例包和工具工作目录。
10. 把任务分配给标注者。

### 7.2 标注者工作

标注者执行：

1. 打开病例包或上次保存的工作文件。
2. 查看本病例包含哪些序列。
3. 查看每个目标组需要处理哪些器官。
4. 编辑一个或多个目标组。
5. 随时保存并关闭，之后继续。
6. 结束时选择提交完成、提交复查或报告阻塞。

### 7.3 提交后

平台操作者或脚本执行：

1. 只导出本次声明提交的目标组。
2. 检查 `review_id`、`target_id`、`image_id` 和基础标签校验值。
3. 检查器官名称和标签值。
4. 检查图像与标签的数组大小、间距、原点、方向和坐标变换。
5. 检查空标签和未知器官。
6. 对通过的目标组创建新标签版本。
7. 对失败的目标组生成问题报告。
8. 更新标注任务和资产登记册。

空间检查失败时，不能只复制图像头信息来“修好”文件。必须证明体素网格一致，或执行明确的最近邻重采样并创建新文件版本。

## 8. 已确认标签怎样继续修改

人工确认标签不是永远锁死。需要修正时：

1. 创建新的标注任务。
2. 新任务引用旧 `label_id` 和文件校验值。
3. 使用匹配基础版本的 `.mcs`，或者重新生成工作目录。
4. 编辑期间结果仍是草稿。
5. 再次提交并通过检查后，创建新的人工确认标签版本。
6. 旧标签和已经使用旧标签的训练数据快照保持不变。

## 9. 多位标注者怎样协作

第一阶段不用在线锁服务，只需：

1. 任务清单可选保存 `assignee`。
2. 协调者不把同一个目标组同时分给两个人。
3. 同一病例的不同目标组可以并行分配。
4. 提交时检查任务、目标组、标注者和基础标签版本。
5. 第二人复核时创建新任务，不覆盖第一人的结果。

后续服务化再增加在线领取、超时回收、强锁、通知和仲裁工作台。

## 10. Mimics 怎样接入

Mimics 是工具适配器，不承担平台状态机和数据治理。实现采用两个清楚分离的运行环境：

| 运行侧 | 负责 |
| --- | --- |
| 外部现代 Python | 病例包检查、医学格式读写、桥接缓冲区、启动 Mimics、空间 QC 和提交入库 |
| Mimics Python 3.5.2 | 调用 Mimics API，导入 DICOM、切换 image set、创建和导出 Mask、保存 `.mcs` |

第一阶段的完整调用顺序是：

```text
sp mimics prepare
-> sp mimics open
-> 标注者在 Mimics 编辑并保存
-> Script / Scripting Library / SP - Submit Review
-> sp mimics finalize
-> 平台 QC 和标签版本登记
```

保存 `.mcs` 只代表保留进度。提交脚本只写出 Mask 缓冲区和提交意图；`finalize` 完成医学格式转换、空间检查和平台注册。

初始标签和提交结果优先使用逐器官一字节布尔缓冲区加 JSON manifest 交换。是否能安全使用 Mimics 原生文件导入导出，由本机 POC 决定；轴顺序和坐标变换不得凭经验硬编码。

一个 `.mcs` 第一阶段只对应一个 `review_id`。多序列图像平等存在，每个目标组绑定明确的 `image_id`，脚本在操作 Mask 前显式切换 image set，不设置默认 primary/reference。

第一阶段允许同一人兼任平台操作者和标注者：操作者运行准备与收尾命令，标注者只在 Mimics 中编辑并运行一次提交脚本。稳定后再把三个外部命令封装为统一启动入口，不先建设跨进程服务或任务队列。

完整代码边界和标注者操作见[Mimics 适配器设计与开发流程](mimics_adapter_design.md)，技术事实见[Mimics 技术参考](mimics_reference.md)，验证步骤见[Mimics POC 计划](mimics_poc_plan.md)。

## 11. 图像和 Mask 的导入导出

Mimics 21.0 官方资料明确支持 DICOM、BMP、TIFF、JPEG 和 raw 图像；当前资料没有证明它原生完整支持 NIfTI 或 MHD/MHA。

因此第一选择是：

- 原始图像优先用 DICOM 创建图像集。
- 外部标签必要时由外部 Python 读取，再注入绑定到正确图像集的 Mimics Mask。
- 提交时可以导出单个 Mask，也可以按目标组导出全部 Mask。
- 输出目录按 `image_id/organ` 组织，避免多序列混淆。

`.mcs` 保存 Mimics 工作现场，适合作为中间进度文件，但不是平台唯一数据来源。跨机器和跨版本能力必须实际验证。

## 12. 候选标签生成为什么仍是独立域

标注入口可以提供“先生成候选标签”的动作，但模型运行仍属于候选标签生成域，因为：

- 模型可能运行在外部 GPU 服务器。
- 输出必须保存模型、算法版本和参数。
- 同一生成能力还要服务无人值守的批量推理。
- 人工标注只负责查看和修正结果。

第一阶段可以由平台操作者先运行生成脚本，再把候选标签放入病例包。Mimics 不需要直接启动模型。

## 13. 一个多序列、多标注员示例

假设一个病例有平扫、动脉期和门静脉期，三个序列都需要标注：

1. 平台登记三个图像记录。
2. 一个病例工作单元引用这三个序列。
3. 标注任务为每个序列建立独立目标组。
4. 标注者 A 处理平扫腹部器官。
5. 标注者 B 处理门静脉期血管。
6. 两人的输出分别绑定各自图像和空间信息。
7. 平扫和门静脉期目标组可以先提交并创建新标签版本。
8. 动脉期血管无法确认时，只有该目标组进入待复查。
9. 标注者 C 通过新任务复核动脉期目标组。
10. 全部目标组完成后，病例任务状态才变为完成。

## 14. 第一阶段开发清单

必须实现：

- 患者、检查和序列分组。
- 图像集、目标组和任务清单。
- 保存进度、提交完成、提交复查和报告阻塞。
- 基础标签版本检查。
- 追加式标签版本。
- 图像与标签空间检查。
- 病例包提交前检查。
- Mimics 工作站诊断和 P01/P02/P04/P05/P06 能力探针。
- 机器可读且人能理解的问题报告。

Mimics Gate A 通过后实现：

- 外部 `prepare`、`open`、`finalize` 命令。
- Mimics 内 `sp_open_review.py` 和 `sp_submit_review.py`。
- 逐器官布尔缓冲区和 manifest 桥接。
- 任务专属 `.mcs`、Mask metadata 和选择性导出。

Gate B 通过后再实现：

- 面向标注者的统一启动入口。
- 更完整的多人进度汇总。
- 标注入口一键生成候选标签。

服务化后再实现：

- 在线领取和锁定。
- 异步提交与退回。
- Web 界面。
- 任务队列。
- 权限、通知和仲裁。

## 15. 判断是否过度设计

准备增加一项第一阶段能力时，先回答：

1. 没有它是否会造成数据错位、覆盖或无法追溯？
2. 当前少量病例闭环是否真的会用到它？
3. 是否可以先用一个清单字段或单个脚本解决？

如果前两个答案都是“否”，并且第三个答案是“是”，就先采用简单实现。
