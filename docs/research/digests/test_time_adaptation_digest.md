## 1. 为什么保留这份文档

这份文档回答一个后期问题：当平台已经能稳定完成标注、训练和离线批量推理后，是否要让模型在新数据、新医院、新扫描协议或用户交互中继续适应。

当前阶段不应该把 TTA、持续学习或交互式学习作为主线。原因很简单：这些方法依赖稳定的数据注册、标签状态、训练快照、评估集和模型版本管理。现在这些地基还在设计阶段，过早引入会让平台边界变模糊。

## 2. 与当前平台的关系

| 方向 | 可以解决的问题 | 当前是否进入主线 |
| --- | --- | --- |
| TTA | 推理时让模型适应当前数据分布 | 否，后期研究 |
| 持续学习 | 用新病例持续更新模型 | 否，后期研究 |
| 交互式学习 | 利用用户修正改进模型或输出 | 否，标注流程先保留接口 |
| 主动学习 | 选择最值得人工审核的病例 | 可以作为 label policy 的后期扩展 |

第一阶段平台只需要保留这些接口：

1. 推理输出先登记为 `candidate_label`。
2. 人工修正后可以成为 `verified_label`。
3. 策略接受的高质量伪标签可以成为 `accepted_pseudo_label`。
4. 每次训练都生成固定的 Dataset Snapshot。
5. 模型版本必须记录训练数据、标签准入策略和评估结果。

这些接口建好以后，后续才有条件讨论模型是否持续更新。

## 3. 不应过早采用的原因

| 风险 | 说明 |
| --- | --- |
| 数据泄漏 | 如果训练/验证/测试拆分没有按病例或患者冻结，持续学习会污染评估 |
| 标签来源混乱 | 用户修正、伪标签、自动预测混在一起，会让模型训练来源不可追溯 |
| 模型退化难发现 | 新数据让模型变好还是变坏，需要稳定评估集判断 |
| 工程闭环变重 | 在线更新、回滚、版本对比和审计都需要额外系统 |
| 责任边界不清 | 人改的是标签、模型、还是后处理规则，必须能分清 |

因此主蓝图选择“离线批量推理先跑通”，而不是一开始就做在线学习或自动持续更新。

## 4. 后期可以怎么接入

推荐把这些能力放在 `Model Improvement` 层，而不是放进标注工具或 nnUNet Adapter 内部。

```text
offline prediction
        ↓
candidate_label
        ↓
human review / qc policy
        ↓
accepted_pseudo_label or verified_label
        ↓
new Dataset Snapshot
        ↓
optional model update experiment
        ↓
Model Registry comparison
```

这样做的好处是：模型更新永远基于一个可复现的数据快照，而不是临时从标注工具里抓一批文件训练。

## 5. 评估前置条件

只有满足下面条件，才建议真正启动 TTA/持续学习/交互式学习实验：

1. 已有稳定的病例注册表。
2. 已有任务级 label map。
3. 已有可复现 Dataset Snapshot。
4. 已有冻结评估集。
5. 已有模型版本记录。
6. 已有标签来源和训练准入策略。
7. 已有回滚机制，至少能恢复到上一版模型。

缺少这些条件时，模型更新实验很容易看起来有效，但无法解释为什么有效，也无法判断是否值得进入平台。
