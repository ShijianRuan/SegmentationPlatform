## 1. 为什么保留决策编号

主蓝图应当易读，不适合反复展开每次讨论过程。本文件保留稳定编号，方便后续说明“为什么这样设计”。

当设计改变时：

1. 先更新对应决策及理由。
2. 再同步平台蓝图、数据模型和实现计划。
3. 不在本文件保存长篇会议讨论。

## 2. 平台范围和实现边界

| 编号 | 决定 | 为什么 |
| --- | --- | --- |
| ADR-001 | 平台围绕病例、图像、标签、训练数据和模型关系建设，不以某个工具为中心 | 标注软件、训练框架和推理算法都可能替换 |
| ADR-006 | 先复用 nnUNet，但通过工具适配器接入 | 现有代码已有可用基础，同时为其他框架保留入口 |
| ADR-008 | 第一阶段使用离线文件包和脚本串联 | 标注电脑与训练服务器可能分离，文件方式更容易先验证 |
| ADR-009 | 第一阶段部署形态是离线批量推理 | 当前重点是数据回流，不是在线服务 |
| ADR-010 | Web 界面和流程调度器后置 | 它们依赖稳定的数据和操作规则 |
| ADR-011 | 代码和文档按人工标注、模型训练、候选标签生成三个域组织 | 便于定位实现，又不把三者误解为三个独立平台 |
| ADR-035 | 一个独立三维体素网格对应一个 Image Artifact；来源格式原样保留，格式转换或重采样创建派生记录 | 多序列和多模态没有默认主次，覆盖原文件会破坏追溯 |
| ADR-036 | 缺失元数据显式记录为 `partial` 或 `index_only`，并分别判断标注、训练和正式评估可用性 | 部分数据仍可使用，但不能用伪造空间信息换取表面上的统一 |

## 3. 标签和训练数据

| 编号 | 决定 | 为什么 |
| --- | --- | --- |
| ADR-002 | 统一器官名称，但每个训练任务保留自己的整数标签编号 | nnUNet 要求任务内编号连续，统一名称不等于统一训练编号 |
| ADR-003 | 同一份图像和标签可以服务多个训练任务 | 局部器官、粗分割和全身任务会复用数据 |
| ADR-004 | 候选标签可以进入训练，但来源状态不能改变 | 高质量模型标签可以利用，同时不能伪装成人工真值 |
| ADR-012 | 质量检查结果是证据，不是标签生命周期状态 | “来源是什么”和“检查是否通过”是不同问题 |
| ADR-013 | 病例包包含标注所需名称映射，不包含训练任务整数编号 | 人工标注不应依赖 nnUNet 任务编号 |
| ADR-016 | 某次训练是否采用标签，只写入训练数据快照 | 避免在标签记录和训练快照中重复保存同一决定 |
| ADR-017 | 器官名称表不保存全局输出编号 | CT 和 MR 合并结果可以使用不同编号，强行统一会制造冲突 |
| ADR-019 | 标准多类 nnUNet 遇到目标标签不完整时，第一阶段排除该病例 | 当前转换脚本会把缺失 mask 静默保留为背景 |
| ADR-024 | 多序列病例不强制主图像和参考图像 | 多个序列可能都要独立标注，任务应直接声明目标 |
| ADR-025 | 病例包工作目录可以变化，但关键输入和提交结果分别记录校验值 | 标注过程中 `.mcs`、报告和进度会变化，整包锁死不实用 |
| ADR-026 | 数据离开受控原始区前必须完成可追溯的去标识检查 | 患者哈希只解决关联，不能证明文件名、DICOM 和日志没有直接标识 |
| ADR-027 | 标注任务按目标组提交 | 整例一次提交过于僵硬，逐器官提交又会产生过多状态 |
| ADR-031 | 只记录当前任务关心器官的覆盖状态：覆盖、未覆盖或不确定 | 第一阶段不建立复杂全身本体，但必须阻止未知区域被当作背景 |
| ADR-032 | 训练数据快照必须冻结完整的结构化 `label_policy`；`TaskDefinition` 只作为后续可选的默认模板 | 阶段 A 无需实现模板继承，但不能丢失训练准入规则和可复现性 |
| ADR-033 | 标签的生成血统按 segment 记录在 `lineage.contributing_generators`，独立于文件级 `parent_label_id`，人工修正时必须继承上游生成器 | 文件级修订指针无法表达每器官血统；人工修正会把来源改成 `manual_review` 而抹掉生成器，使 ADR-018 的标签来源泄漏检查无法执行 |
| ADR-034 | 任务标签编号要求“从 0 连续、无空缺”；把多个结构合并成一个训练类别是合法需求，但合并必须**显式且经确认**，不应靠多个器官名重复填写同一整数来表达 | “整数绝不重复”会误杀合法的合并任务；但靠重复整数表达合并很脆弱（见下方说明） |

> **ADR-034 待确认事项（重要）**
>
> 引出本决定的 `CT6_KidneySpleen` 现有写法存在两个隐患，采纳前必须先核对：
>
> 1. **左右可能写反。** 当前是 `kidney_right=2`、`kidney_cyst_left=2`、`kidney_left=3`、`kidney_cyst_right=3`，即**左侧囊肿被并入右肾的编号**、右侧囊肿并入左肾。从解剖上看更可能应当左配左、右配右。这是数据/医学意图问题，需由任务负责人确认是有意为之还是旧配置笔误，**平台不擅自修改**。
> 2. **语义依赖字典顺序。** 转换脚本 `Action1_ConvertLabeledToTrainData.py` 在多个名称共享同一整数时只保留**首次遇到的名称**写入 `dataset.json`，因此合并类别叫什么取决于 `ModelMap` 中的书写顺序，而非显式声明。
>
> 推荐方向（阶段 A 不强制实现）：用显式的分组类别结构表达合并，例如 `{value: 2, name: kidney_right, members: [kidney_right, kidney_cyst_left]}`，让“这个类别由哪些结构组成、对外叫什么”一目了然，不再依赖重复整数和字典顺序。在改用显式结构前，校验器对“同一整数多名称”应给出**警告并要求人工确认**，而不是直接放行。

## 4. 人工标注和版本

| 编号 | 决定 | 为什么 |
| --- | --- | --- |
| ADR-005 | 第一阶段允许同一人完成标注和确认，但保存不等于提交 | 减少人力要求，同时防止中间进度被误当最终标签 |
| ADR-020 | 标注任务进度与标签生命周期分开 | 进行中、待复查和阻塞描述工作过程，不描述标签来源 |
| ADR-022 | 人工确认标签可以继续修订，但不能覆盖旧版本 | 医学标签可能需要返修，旧训练仍必须可以复现 |
| ADR-023 | 第一阶段支持多人处理不同目标组，不建设在线锁服务 | 任务分配和基础版本检查足以支持早期协作 |

## 5. Mimics

| 编号 | 决定 | 为什么 |
| --- | --- | --- |
| ADR-007 | Mimics Research 21.0 是优先验证的标注工具，不是平台唯一底座 | 官方资料能证明部分能力，但完整导入导出仍要本机验证 |
| ADR-021 | 先验证直接文件路径，只有必要时才使用双 Python 文件桥接 | 双运行环境会增加维护成本，不能在验证前写成平台前提 |

Mimics 可行性验证必须回答：

1. 多患者、检查和序列能否与平台病例清单正确对应。
2. 每个 Mask 能否稳定绑定到正确图像集。
3. 直接导入导出是否足够。
4. 图像索引到物理坐标、Mask 数组轴顺序和导出空间能否证明。
5. 脚本参数、导入、命名、指定导出和日志是否可控。
6. 保存、提交、待复查、重新打开和多人基础版本冲突能否正确处理。

## 6. 评估、候选标签和研究能力

| 编号 | 决定 | 为什么 |
| --- | --- | --- |
| ADR-014 | 少样本先作为实验协议，不建立通用工具适配器 | 不同少样本方法的输入输出差异很大；低样本 nnUNet 仍是 nnUNet |
| ADR-015 | 候选标签生成域记录许可和使用限制，但不独自作法律裁决 | 许可影响整个平台，不只影响生成步骤 |
| ADR-018 | 正式评估只使用独立参考标签 | 防止模型在自己或上游模型生成的标签上自我确认 |
| ADR-028 | 每次正式评估创建独立、不可修改的评估记录 | 同一模型会在不同评估集上多次评估，结果不能互相覆盖 |
| ADR-029 | 每次离线候选生成创建批次记录 | 必须处理部分失败、重试、重复运行和中断恢复 |
| ADR-030 | 模型登记后不能自动获得正式候选标签生成资格 | 还需检查基本质量、来源和使用限制 |

## 7. 标签状态怎样理解

| 生命周期状态 | 含义 | 是否自动进入训练 |
| --- | --- | --- |
| `source_label` | 外部数据集自带标签 | 否，由本次训练规则判断 |
| `candidate_label` | 模型、算法或规则生成的候选标签 | 否，由本次训练规则和质量证据判断 |
| `draft_label` | 人工正在修订或等待复查的草稿 | 否 |
| `verified_label` | 人工明确提交且平台检查通过的新版本 | 通常允许，但仍受任务和使用限制约束 |
| `rejected_label` | 已明确拒绝使用 | 否 |

`accepted_pseudo_label` 不是底层状态。如果某个候选标签被一次训练采用，训练数据快照记录“本次采用”，原标签仍保持候选状态。
